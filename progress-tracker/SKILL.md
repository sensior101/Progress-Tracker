# Progress Tracker

산출물은 **업무 JSON 파일과 공용 사이트 링크**다. 실제 체크·캘린더·포인트·상점은 https://sensior-progress-tracker.pages.dev 에서 사용한다. HTML, 로컬 지갑, 별도 로그인·거래 코드를 프로젝트에 복사하지 않는다.

## 생성·갱신

1. 프로젝트의 README, docs, 빌드 설정, 관련 코드·테스트와 최근 변경을 확인한다. 이전 체크리스트를 그대로 추측해서 완료 처리하지 않는다.
2. 기본적으로 3~7개 단계를 만들되 사용자가 요청한 구조를 우선한다. 업무는 완료 여부를 판단할 수 있는 한 줄로 쓰고, 같은 책임을 중복 업무로 쪼개지 않는다.
3. 기본 출력은 `docs/progress.json`이다. 사용자가 경로를 지정했거나 이미 진행 JSON이 있으면 그 경로를 사용한다. HTML 페이지는 새로 만들지 않는다.
4. 기존 JSON이 있으면 **projectId와 업무 id를 유지**하고 필요한 설명·업무만 갱신한다. 서버에서 재등록할 때 같은 ID의 완료 상태·일정과 이미 받은 보상은 유지된다.
5. 신규 프로젝트는 `projectId`에 새 UUID를 한 번 생성한다. 기존 JSON·서버에서 내려받은 데이터에 ID가 있으면 새로 만들지 않는다. 이전 HTML을 JSON으로 옮길 때는 내부 data JSON을 추출한다. 기존 projectId가 없으면 프로젝트 이름을 유지하고 `name-` + 프로젝트 이름 UTF-8 SHA-256 값으로 지정해 이전 서버의 프로젝트 식별 방식과 맞춘다.
6. JSON 문법, 페이지 안의 고유 업무 ID, 필수 항목과 실제 구현 근거를 확인한다. `updated`를 갱신일로 바꾼다.
7. 완료 보고에는 JSON 경로와 [공용 사이트](https://sensior-progress-tracker.pages.dev) 링크를 제공한다. 사이트에서 GitHub 로그인 후 **JSON 가져오기**로 등록하거나 갱신하도록 안내한다.

## 업무 작성 기준

- `text`: 구체적인 업무 이름. 예: `업무 마감일 변경하기`.
- `note`: 보드에서 읽는 짧은 요약.
- `details`: 모든 신규 업무에 작성하는 상세 설명. 목적·구현 순서·완료 기준을 여러 문단으로 구분하고, 관련 파일·API·실패 상황을 실제 프로젝트 근거로 구체화한다. 제목을 길게 반복하는 설명은 피한다.
- `done`: 해당 업무의 완료 기준을 확인했을 때만 true. 코드 구현, 자동 테스트, 배포·실제 연동 검증은 구분한다. 확인하지 않은 테스트 성공이나 동작을 근거로 쓰지 않는다.
- `date`: 선택 항목인 등록 날짜. 사용자가 지정했거나 근거가 있는 일정만 넣는다. 완료 체크 시 서버가 한국 시간 기준 그날 날짜를 등록하므로 과거 완료일을 임의로 추정하지 않는다.
- 기존 업무의 `details`가 없거나 짧으면 보완하되 ID·완료 상태·일정은 유지한다.

## JSON 형식

```json
{
  "projectId": "83ea0998-8415-4610-b804-c0e7587d44c4",
  "project": "프로젝트 이름",
  "subtitle": "한 줄 설명",
  "updated": "2026-11-04",
  "phases": [
    {
      "title": "1. 기본 기능",
      "description": "단계 설명",
      "tasks": [
        {
          "id": "ui-login",
          "text": "로그인 화면 연결하기",
          "done": false,
          "note": "기존 인증 API 재사용",
          "details": "목적\n기존 계정으로 로그인하고 본인 데이터에 접근하도록 한다.\n\n구현 순서\n1. 기존 인증 API와 세션 처리 코드를 확인한다.\n2. 입력 화면을 기존 API에 연결하고 성공·실패 안내를 구분한다.\n3. 로그인 유지와 로그아웃을 연결한다.\n\n완료 기준\n정상 로그인·로그아웃, 잘못된 입력과 만료 세션 처리를 확인한다. 실제 프로젝트에서 확인한 파일·API 이름으로 설명을 구체화한다."
        }
      ]
    }
  ]
}
```

예시의 projectId는 그대로 복사하지 않고 신규 프로젝트별로 생성한다. 업무 `id`는 고유한 짧은 kebab-case를 사용한다. `details`는 HTML이나 실행 코드가 아닌 20,000자 이하의 일반 문자열이다. 서버 등록 한도는 프로젝트당 업무 1~300개다.

## 계정과 포인트

사이트가 로그인·저장·보상을 담당한다. 업무당 최초 완료 보상은 10P이며 같은 업무를 다시 체크하거나 재등록해도 중복 지급하지 않는다. 포인트를 늘리려고 동일한 업무를 여러 ID로 생성하지 않는다. CLI에서 포인트·잔액·구매 내역을 JSON에 넣거나 변경하지 않는다.
